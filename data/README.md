# Combat data (ships, hostiles, buildings)

- **Ships:** Ship list and combat resolution use **`ships_extended/`** only: `ships_extended/index.json` plus per-ship `ships_extended/<id>.json` (tier + level stats). Built from upstream data via `scripts/build_ship_registry.py` and `cargo run --bin normalize_data_stfc_space`. Game hull_id (from sync) → Kobayashi ship id for Roster mode is in **`hull_id_registry.json`** at the data root; regenerate with `node scripts/build_hull_id_registry.mjs`.
- **Hostiles:** Loaded from `hostiles/index.json` plus per-id JSON files in the same directory. Refresh from cached data.stfc.space detail JSON with `cargo run --bin normalize_hostiles_stfc_space` (inputs under `data/upstream/data-stfc-space/hostiles/`). Optional env: `STFCSPACE_HOSTILES_VERSION`, `STFCSPACE_HOSTILES_SOURCE_NOTE`. STFCcommunity baseline: `cargo run --bin normalize_stfc_data` (different id scheme: string slugs).
- **Buildings:** Loaded from `buildings/index.json` plus per-building JSON files.

## Provenance

- **Index files** include optional `data_version` and `source_note` (e.g. `"data_version": "stfccommunity-main"`, `"source_note": "STFCcommunity baseline (outdated ~3y)"`). These document where the data came from and help detect drift.
- **Source:** Data is typically produced by the normalizer from STFCcommunity or other community sources. See the normalizer and `data_version` / `source_note` in each index for the current baseline.
- **Validation:** Run the test suite; `data_provenance_and_validation` (or similar) tests that indexes load and optional version fields are present. For manual checks, compare a subset of ship/hostile stats to a known source (e.g. toolbox or game).

## Schema

- **Ships:** See `src/data/ship.rs` (`ExtendedShipRecord`, `ShipRecord`). Extended files in `ships_extended/<id>.json` have `tiers[]` (per-tier combat stats) and `levels[]` (shield/health bonuses); resolved at request time to `ShipRecord` for a given tier/level. Fields include attack, hull_health, shield_health, shield_mitigation, apex_shred, isolytic_damage, etc. Optional **`abilities`**: hull abilities from upstream `ability` rows, mapped through `data/upstream/data-stfc-space/ship_ability_catalog.json` at normalize time (or hand-edited). Resolver: `src/data/ship_ability_resolve.rs`; pipeline: [docs/DESIGN.md](../docs/DESIGN.md) §3.6 (Ship hull abilities).
- **Hostiles:** See `src/data/hostile.rs` (`HostileRecord`). Core combat fields: armor, shield_deflection, dodge, hull_health, shield_health, shield_mitigation, apex_barrier, isolytic_defense, mitigation floor/ceiling, mystery factor. Records from `normalize_hostiles_stfc_space` also include upstream metadata (`loca_id`, `faction`, `upstream_ship_type`, `hull_type_raw`, `systems`, …), full aggregated/offensive stats (`stat_health`, `accuracy`, `armor_piercing`, …), and preserved `components` / `ability` / `resources` JSON arrays. **Defender faction for abilities:** [`HostileRecord::opponent_faction_tag`](../src/data/hostile.rs) maps `faction.id` / `faction.loca_id` (see `summary-hostile` + `translations-factions.json` `faction_name`) to [`OpponentFactionTag`](../src/combat/types.rs). Factions without a combat enum (Q-Continuum, Exiles, Node, Maverick, etc.) resolve to `Unknown` on purpose — see module docs in `hostile.rs`.
- **Buildings:** See `src/data/building.rs` (`BuildingRecord`). Each building has `levels` with `bonuses` (`stat`, `value`, `operator`, optional `conditions`/`notes`). Index is `data/buildings/index.json` (`BuildingIndex`).

## Buildings: sync and optimizer

Buildings are fully modeled for ship combat. Mapping gaps are tracked in [building_gaps.md](../docs/building_gaps.md); station defense remains explicitly out of scope in [NOT_ROADMAP.md](../docs/NOT_ROADMAP.md#buildings--scenarios).

- **Where the optimizer reads building state:** `profiles/{profile_id}/buildings.imported.json` (see `profile_index::profile_path(profile_id, BUILDINGS_IMPORTED)`). The scenario loader uses the resolved profile id (default when none specified) and loads that file; building bonuses are merged into the player profile for combat.
- **Ops level for building context:** Building level rows can have `ops_min`/`ops_max`; only rows matching the player’s Operations level are applied. The optimizer infers ops level from **Operations Center** (building id `ops_center`, game bid 0) in the synced buildings list. If sync does not include ops_center or bid 0 does not resolve, ops_level is `None` and all level rows are applied. You can override by setting `profile.ops_level` in the profile JSON so simulation works without sync.
- **Strategy for new buildings:** Game `bid` → Kobayashi building `id` is resolved by `building_bid_resolver::load_bid_to_building_id` using (1) `data/upstream/data-stfc-space/translations-starbase_modules.json` (name match or fallback `building_{bid}` when that id exists in the index), and (2) any index entry whose id is `building_{bid}` is added to the map so sync for a new bid still resolves if that building file exists. To support a new building: run the stfc.space import script so the building appears in the index (and optionally update translations), or add a `building_{bid}.json` and an index entry so the resolver picks it up.
- **Validation:** Building validation warns when a bonus uses a `buff_*` stat (ignored by combat until mapped). Add mappings in `data/buildings/buff_id_to_stat.json` and re-run the import script so combat-relevant bonuses use engine stat names. See `data/upstream/data-stfc-space/BUFF_ID_TO_STAT_NAME.md`.
- **Tooling:** `cargo run --bin building_combat_bonuses` prints theoretical max combat bonuses (all buildings at max). Use `--profile <id>` to print effective combat bonuses for that profile’s synced building levels (ops_level from Operations Center, ShipCombat mode). If the profile has no buildings file or empty list, the binary falls back to “all at max” for that run.

## Research: catalog and optimizer

- **Catalog:** `data/research_catalog.json` (KOBAYASHI schema). Each item has `rid` (game research id), optional `name` (from `translations-research.json` `research_project_name`), `level_value_mode`, and `levels` (array of `{ level, bonuses: [{ stat, value, operator, ...conditions }] }`). Imported records use `"snapshot"`: one row contains the complete bonus for that rank. Authored records that omit the mode retain `"cumulative"`: their level increments compose through the owned level. Level zero contributes nothing; above-maximum levels use the catalog maximum. Empty or missing snapshot ranks contribute nothing. Canonical overrides retain their separate `snapshot_by_level` contract.
- **Combat channels and conditions:** Supported profile keys include the ordinary ship stats, isolytic and apex bonuses, and separate **`accuracy`**, **`armor_piercing`**, and **`shield_piercing`** fractions. The three piercing stats scale their respective base stats before hostile mitigation; they do not map to generic damage-through `pierce`. Explicit condition fields determine routing through profile, faction, scenario, or timed-effect paths; see [research_conditional_routing.md](../docs/research_conditional_routing.md).
- **Canonical overrides:** Ten bundled combat effects explicitly select rank snapshots; the eleventh override is empty to exclude a deployment-only cargo buff. Authored overrides retain cumulative behavior when `snapshot_by_level` is absent or false. The [canonical source audit](../docs/research_conditional_routing.md#canonical-source-audit-2026-10-20) records the five earlier modifier/condition mismatches and their client-verified corrections. The three base-defense buffs and Morale shield repair compile at round start through dedicated stats, with raw `value_unit: "fraction"` mappings and explicit status gates. Selected static evidence is retained in `research/client_verified_research_2026-10-20.json`.
- **Synced savepoint vs combat:** `profiles/{profile_id}/research.imported.json` stores **every** merged `rid` + `level` from the mod (cumulative across syncs). Kobayashi does **not** drop rows just because a `rid` is missing from the catalog — that file is your local research state. The maintainer catalog only controls **which** synced projects contribute **ship combat** stats in simulate/optimize; unmapped `rid`s are skipped for combat only.
- **Where the optimizer reads research state:** `profiles/{profile_id}/research.imported.json` (synced by the mod; each entry is `rid` + `level`). When building the scenario, the loader calls `merge_research_bonuses_into_profile` so research bonuses are applied to combat. If the catalog is missing or a rid is not in the catalog, that research is skipped for combat (no crash); the row remains in `research.imported.json`.
- **Buff → stat mapping (import):** `node scripts/import_stfcspace_research.mjs` resolves each research buff in this order: inline `RESEARCH_BUFF_MAPPING`, `data/research/buff_id_to_stat.json`, `data/buildings/buff_id_to_stat.json`, `data/research/loca_id_to_stat.json` (API `buff.loca_id`), then description and display-name heuristics from `translations-research.json`. Explicit mappings may emit several stats and preserve supported condition fields. The importer excludes recognized suspect unconditional scopes such as Armada-only, PvP, station-defense, and ship-specific descriptions. Combat evaluates structured fields, not prose; an omitted or over-broad condition still requires a corrected mapping backed by evidence.
- **Grade 4+ Direct Hit:** Research `2999437` / buff `1994654654` emits all three base piercing stats with `attacker_min_grade: 4`. Rank 2 contributes `0.24` per channel, rank 10 contributes `0.80`. Ship `grade` is preserved through upstream normalization and resolution. Known grade 4+ matches; grade 3 or unknown grade does not. Scenario compilation and scenario-aware research summaries apply the same gate. Grade-gated rows cannot enter the unconditional/faction-only merge or timed seats; the current implementation supports only grade-only restrictions on these three stats.
- **Flat vs percentage values:** The importer normalizes percentage-like values and, for `value_is_percentage: false`, accepts small fractional bonuses for the usual combat stats; very large flat hull/shield integers remain skipped (no defined conversion to profile multipliers).
- **Refresh from upstream:** (1) Populate `data/upstream/data-stfc-space/research/{id}.json` (tracked) via `node scripts/fetch_stfcspace_research.mjs`, a mirror tarball, or any bulk job — **the import script never downloads per-rid JSON over the network.** (2) `node scripts/import_stfcspace_research.mjs --from-upstream --limit 0` reads those files and writes `data/research_catalog.json`. Use `--limit N` or `--rid a,b` for subsets; `--dump-unmapped` for buff ids still missing resolution. If no item emits combat bonuses, the script leaves `data/research_catalog.json` unchanged.
- **Improving mapping coverage (why growth is mapping-limited):** Resolution order is explicit buff/loca JSON → building buff overlap → description/name heuristics in `import_stfcspace_research.mjs`. To add more combat rows: (1) **`data/research/buff_id_to_stat.json`** — highest precision when one buff id is ambiguous under loca heuristics or shared across unrelated projects. (2) **`data/research/loca_id_to_stat.json`** — stable when many buffs share the same `loca_id` and one stat is correct globally. (3) **Extend `data/buildings/buff_id_to_stat.json`** — when research reuses the same buff id as starbase modules. (4) **Tighten heuristics** in the import script only when a rule is safe (avoid widening patterns that mis-map economy/station lines). (5) **`--dump-unmapped`** after a full local import — sort by `count`, inspect `example_rids`, cross-check translations and in-game tooltips, then add buff-id overrides (optional: capture to `data/research/unmapped_buff_backlog.json`; that path is gitignored if you regenerate it locally). (6) **Engine keys** — stats must exist in `normalize_profile_combat_stat` (e.g. apex) before mapping them does anything in simulate/optimize. **`accuracy`** is supported end-to-end (profile merge + hostile mitigation via `AttackerStats` in `scenario.rs`; treated as a fractional multiplier on ship base accuracy, same catalog convention as `weapon_damage`).
- **Suggestion helper:** `node scripts/suggest_research_buff_mappings.mjs` scans cached `research/*.json` and prints CSV rows with heuristic `suggested_stat` for human review (not authoritative).
- **Flat hull/shield HP from research:** When upstream sets `value_is_percentage: false` with unsupported large integers, the importer skips those bonus entries (no agreed conversion to the profile’s fractional hull/shield **multipliers**). Snapshot records retain empty ranks whenever another rank has a mapped contribution. Improving coverage requires an explicit, calibrated conversion rule; do not invent one silently.

## Upstream data-stfc-space mapping layer

- **Purpose:** JSON under `data/upstream/data-stfc-space/mapping/` documents upstream data.stfc.space artifacts: every root-level `summary-*.json`, `translations-*.json`, `ship_id_registry.json`, and the two markdown guides—**except** bulk per-id caches (`ships/*.json`, `hostiles/*.json`, `research/*.json`), which are described only by glob/pattern.
- **Canonical inventory:** `mapping/upstream_catalog.json` lists each of those files with a short semantic description, primary ids, related translation tables, and Kobayashi touchpoints where applicable.
- **Index:** `mapping/index.json` points at domain mapping files: `upstream_catalog`, `ships`, `hostiles`, `buildings`, `research`, `officers`, `translations`.
- **Per-domain mappings:** `ships.json`, `hostiles.json`, `buildings.json`, `research.json`, `officers.json`, `translations.json` add entity shapes, field notes, and normalization targets.
- **Validation:** `node scripts/validate_stfcspace_mapping.mjs` checks mapping files, that catalog paths exist on disk, that bulk globs have at least one file, and that **every** `summary-*.json` / `translations-*.json` at the upstream root appears in `upstream_catalog.json` (so new upstream drops fail CI until documented). When you add upstream files, extend `upstream_catalog.json` and run the validator.

## Forbidden tech: catalog and partial status

- **Catalog:** `data/forbidden_chaos_tech.json` (source: `data/import/forbidden_chaos_tech.csv`). Import with `cargo run --bin import_forbidden_chaos`. CSV columns: name, tech_type, tier, fid, stat, value, operator.
- **Chaos tech bulk rows:** `summary-forbidden_tech.json` uses `tech_type: 1` for chaos. To regenerate chaos lines from live detail JSON (`https://data.stfc.space/forbidden_tech/{id}.json`), run `node scripts/build_chaos_tech_csv_rows.mjs` and merge stdout into the CSV (then re-run the Rust importer). Values default to index **45** in each buff’s `values[]` (level-46-style calibration, same spirit as S31 in `data/import/README.md`).
- **`fid` mapping (sync match):** Merge uses **game `fid`** from the catalog row to match `profiles/{id}/forbidden_tech.imported.json` from stfc-mod. Rows **without** `fid` never apply for synced players. Maintenance workflow:
  1. Prefer **automatic fill:** place `data/upstream/data-stfc-space/summary-forbidden_tech.json` and `translations-forbidden_tech.json` (same names the stfc.space pipeline uses), then run `cargo run --bin import_forbidden_chaos`. The binary joins normalized CSV **name** → translation text → `loca_id` → summary **`id` (fid)** when the CSV `fid` column is empty.
  2. Otherwise set **`fid` manually** in the CSV (from game/mod payloads or community lists), then re-run the importer.
  3. **CI:** `cargo test` runs `forbidden_chaos::sync_readiness_tests` — the committed catalog must have **no missing `fid`** and **no duplicate `fid`** so regressions are caught early.
- **Where the optimizer reads FT state:** `profiles/{profile_id}/forbidden_tech.imported.json` holds **inventory** (fid, tier, level, shard_count) from stfc-mod. Combat merges **only** the two equipped slots stored on `profile.json`: `equipped_forbidden_fid` and `equipped_chaos_fid` (each optional; must match catalog `tech_type` when set). Bonuses from the catalog (by `fid`) are merged into the player profile; add and mult operators are supported.
- **Client-verified rank curves:** Ablative Armor (`fid` 482782456) carries separate hull/shield `rank_curve` snapshots from client build 272. Select `values[level - 1]`; tier unlocks hull at 1 and shield at 2. Tier 4 / level 20 adds `1.0` to each percentage pool. These curves apply whenever equipped and synced, independent of the legacy scaling flag. Missing, invalid, or out-of-range ranks contribute zero. CSV regeneration preserves existing verified curves by `fid` and stat.
- **Legacy level/tier scaling:** Entries without verified curves retain opt-in `KOBAYASHI_FT_LEVEL_TIER_SCALING=1` (an approximate linear model; see `forbidden_tech_level_tier_scaling_enabled_from_env` in `src/data/profile/mod.rs`). Other tech values still require source verification.
- **Partial / gaps:** Prefer calibrating S31 Torpedo Pods (and similar) from [`upstream/data-stfc-space/forbidden_tech/{fid}.json`](upstream/data-stfc-space/forbidden_tech/473132032.json) when available: use `values[level-1].value` as a percentage → catalog decimal. Some upstream copy is class-specific (e.g. Battleship) while the simulator applies generic profile keys. See ROADMAP for combat-timing uncertainty (profile-only vs per-sub-round).

## Support buffs: request-scoped catalog

Workspace simulations and optimizations can include **request-scoped** support buffs (Cerritos support, Defiant reinforcement, Titan-A Fortification, …). Selections are passed as `support_buffs: string[]` on simulate/optimize/compare API requests and are *not* persisted to `profile.json` — they represent the current fight setup only.

- **Catalog:** `data/support_buffs.json`. The server deduplicates ids, applies `exclusive_group` priority for incompatible choices, and emits warnings for unknown ids.
- **Research-catalog gating:** Some research rows are support-buff-gated — intentionally excluded from normal profile research summaries, merged into combat stats only when the matching support buff is active.
- **Limitations:** Support buffs currently apply to the **attacker side only**. Defender-side alliance buffs and debuffs are not modeled as separate scenario inputs. Non-catalog support values are modeled only where `data/support_buffs.json` has explicit static bonuses or curated gated research ids. When in-game mechanics are uncertain, prefer updating the catalog with provenance notes rather than hard-coding a one-off combat exception.

## Native officer base CoreStats

`native_officer_core_stats.json` contains 302 native OfficerSpec weight/rarity
rows and 100 level-growth rows from the reviewed build-272 static cache. The
float32 multiplication and integer rounding path was also verified in build
273. These are base stats before account, seat and ability bonuses; this catalog
does not resolve Tom Paris's combat Defense source or stacking.

The officer-model loader substitutes native values only when the numeric source
ID and exact upstream file bytes match a catalog binding. The 290 reviewed
upstream bindings each list separate LF and CRLF SHA-256 hashes. Runtime hashes
the original bytes without normalizing them. Changed/unbound files and
unavailable native IDs or levels retain their existing upstream values;
hand-authored LCARS stats bypass this boundary. Upstream JSON remains unchanged.

Regenerate from the reviewed cache and current upstream officer directory:

```sh
node scripts/extract_native_officer_core_stats.mjs --static-cache <static-cache.bin> --upstream-officers data/upstream/data-stfc-space/officers
```

Add `--check` to verify the generated catalog. A new cache digest or changed
upstream binding requires source review before regeneration. See
[the native proof](../docs/STFC_CLIENT_REVERSE_ENGINEERING.md#retained-native-officer-core-stat-source).
