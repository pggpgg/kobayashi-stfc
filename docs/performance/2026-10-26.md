# Simulator throughput measurement, 2026-10-26

This experiment compares the original engine at `884c4701a5d5986d265abb80986a5e77e5936dcb`
with allocation and borrowing changes. Both variants use the same benchmark
source, catalogs, Rust toolchain and release settings. The original engine was
measured and its executable frozen before optimization began.

## Changes

- Replace nine heap buffers per weapon pair with fixed four-lane stack arrays.
  The initialized prefix, batch boundaries, lane order and early-kill behavior
  stay the same.
- Borrow effect slices when every sampled condition passes. Materialize an
  ordered subset only when a condition rejects a row. Reuse the already sampled
  round-start selection for regeneration.
- Skip empty reaction processing and disabled trace activation work. Move a
  phase accumulator when its previous value is no longer needed.
- Borrow officer-stat inputs and stream dynamic contributions. Preserve the
  static-self, static-opponent, dynamic-self, dynamic-opponent arithmetic order.
- Remove unnecessary candidate crew clones and repeated faction-map resolution.

No trial budget, search pruning rule, floating-point operation order, RNG draw,
combat rule, calibration tolerance or optimizer cache version is changed.

## Measurement protocol

The machine is a Ryzen 7 7700X with 32 GiB of RAM, running Windows
10.0.26300. Rust is 1.93.1, LLVM 21.1.8, targeting
`x86_64-pc-windows-msvc`. Both timing executables use the normal release profile:
optimization level 3, fat LTO, one codegen unit, panic abort and stripped symbols.
Neither uses allocation instrumentation, a custom target CPU or additional
compiler flags. The existing High Performance power plan was unchanged.

The engine experiment uses one logical CPU (affinity mask `0x4`) and one Rayon
thread. Each case cycles the same 64 seeds, including a seed larger than 2^53.
Fight counts were chosen using the original engine and then frozen. Each of
eight blocks runs baseline/candidate/candidate/baseline, reversing that order in
alternate blocks. All samples are retained; no outliers are removed. Builds and
other benchmark jobs do not run concurrently with timing.

The paired speedup is the median of each block's mean baseline time divided by
its mean candidate time. The interval is a deterministic 10,000-resample
percentile bootstrap over whole blocks. This describes variation within this
machine's run, not independent-day or other-machine uncertainty. The throughput
gain is `(speedup - 1) * 100`; the time reduction is `(1 - 1/speedup) * 100`.

Each case first checks all 64 seeds with tracing on and off. Before timing, the
driver also compares complete serialized results for 64 trace-off and four
event-trace seeds, including floating-point bits and ordered events. Every
timed sample must retain the same workload, completed fights, rounds, hit
counts, wins, round-limit outcomes and checksum.

The kernel policy is deliberately unchanged. On this machine the engine selects
the AVX2 four-lane path when tracing is off, even when
`KOBAYASHI_EXPERIMENTAL_SIMD_DAMAGE_KERNEL=0`. The original raw summary field
`simd: false` records the requested environment flag, not the selected backend.
Both variants use the same automatic AVX2 selection; these are not forced-scalar
measurements.

Prepared-engine cases exclude catalog loading, officer conversion and setup.
The wrapper case includes setup. The catalog case uses real public ship,
hostile and LCARS definitions, without a player profile. Separate optimizer
measurements include scenario construction and use the public demo profile.

## Historical counter correction

The existing `simulator/combat_3_rounds`, `combat_20_rounds` and
`combat_100_rounds` Criterion inputs terminate in round one. Their oversized
fractional piercing value causes an immediate kill. They remain useful legacy
regression cases, but their names are round limits, not executed work.

The old `benchmark_simulator` command multiplied fights by the configured limit
of 100 when reporting rounds per second. It now consumes results with
`black_box`, sums `rounds_simulated`, and reports the actual average rounds per
fight separately from the limit. Historical rounds-per-second claims based on
that multiplier should not be used as throughput evidence. The committed CI
baseline log is unchanged.

## Reproduction

Use clean public checkouts for both revisions. Do not benchmark from a runtime
containing private player profiles. Set the current directory and
`KOBAYASHI_HOME` to the same checkout, with its required catalogs. Copy each
release executable to a distinct path before building the next variant.

```text
cargo build --release --locked --bin hot_path_bench
python scripts/compare_hot_path.py --baseline ORIGINAL_EXE --runtime . --output INITIAL --blocks 8 --seconds 0.75 --affinity 0x4 --threads 1
python scripts/compare_hot_path.py --baseline ORIGINAL_EXE --candidate OPTIMIZED_EXE --runtime . --output PAIRED --counts-from INITIAL/summary.json --blocks 8 --seconds 0.75 --affinity 0x4 --threads 1
python -m unittest discover -s scripts/test -p test_compare_hot_path.py
```

For stronger build provenance, supply `--baseline-build-manifest` and
`--candidate-build-manifest`. Each manifest binds its executable SHA-256 to the
frozen harness, allocator helper and lockfile hashes, compiler identity and
complete release configuration. The driver rejects differing build settings
and allocation-instrumented executables. It also retains process output and
failure metadata for timed-out or unsuccessful children.

Allocation counts use a separate `--features bench-alloc-count` executable and
`--allocations --iterations 64`. Its timing output is disabled. Counts describe
allocator requests in the selected combat loop, not live or peak heap usage.
