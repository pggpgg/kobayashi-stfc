# Combat-engine fidelity backlog

Planned follow-ups to the 2026-07-08 fidelity pass (PR #252, commit `cd6ff9a7`). Each issue has
(a) a plain-language description and (b) a self-contained prompt for an implementation session.

**Shared context every prompt assumes** (established in PR #252, see
[HOSTILE_ABILITY_COMBAT_NOOP_AUDIT.md](HOSTILE_ABILITY_COMBAT_NOOP_AUDIT.md) "Fidelity pass (2026-07-08)"):

- Hostile abilities flow: upstream `data/upstream/data-stfc-space/hostiles/*.json ability[]` →
  catalog `hostile_ability_catalog.json` (regenerated by
  `scripts/generate_full_hostile_ability_catalog.py`, hand-tuned rows in
  `hostile_ability_catalog_overrides.json`) → `src/data/hostile_ability_resolve.rs` → defender-crew
  seats → counter-fire effect accumulator in `src/combat/engine.rs`.
- Value conventions: upstream `values[].chance: 1` means **100%**; text placeholders shaped like
  `{0:#.#%}` mean the upstream value is a **fraction** (0.75 renders "75%"); catalog
  `attack_multiplier` values are **bonus fractions** (`ProcAttackMultiplier` composes `×(1+value)`);
  `round_cap: N` on a catalog entry gates the seat to combat rounds `1..=N` via
  `AbilityCondition::RoundRange`.
- Verification: `cargo test` (integration tests live in `tests/`, e.g.
  `tests/hostile_fidelity_new_mechanics.rs` shows the end-to-end pattern with real hostile records),
  `cargo clippy --all-targets`, regenerate the catalog and **diff effect_type transitions vs HEAD**
  to prove no unintended reclassification, and update the audit doc's bucket/instance tables.
- Per project policy (docs/NOT_ROADMAP.md): do **not** propose recorded-fight corpus collection;
  ground mechanics in ability text, existing engine hooks, and community-documented behavior.

Ordering is by (hostile instances affected) × (tractability).

## Correctness audit (2026-07-10) — engine bugs fixed outside this backlog

A dedicated audit pass (post-Morale-fix, PR #256) found and fixed five engine correctness bugs and
one validation gap; they are recorded here because calibration bands and golden masters were
re-blessed accordingly:

1. **LCARS dynamic `weapon_damage` operator folding** — `compile_officer_combat_spec_impl`
   emitted full factors into `AttackMultiplier`, which the accumulator consumes as an additive
   bonus fraction: every non-static officer weapon-damage buff was over-applied by +100
   percentage points (`multiply 1.2` dealt ×2.2) and `sub` debuffs flipped into buffs.
   Now folds like the Pierce family (`multiply v → v−1`, `sub v → −v`, `add v → v`).
   Test: `tests/lcars_weapon_damage_operator_convention.rs`.
2. **Round-start `ShotsBonus` expiry off-by-one** — both round-start push sites used
   `round_index + duration` against a prune of `expires_round >= round_index`, so extra-shots
   procs (attacker and hostile counter-fire) lasted duration+1 rounds. Now `+ duration − 1`
   (the documented ring convention). Test: `tests/shots_bonus_expiry.rs`.
3. **Player self-burn tick scaled by the outbound apex factor** — a hostile's apex barrier
   wrongly suppressed the player's own burning damage. Test:
   `tests/self_burn_apex_independence.rs`.
4. **Effectiveness helpers scaled full-factor effects as bonuses** — Pike-style bridge
   effectiveness and captain-maneuver scaling multiplied `CritDamageMultiplier` (a full factor)
   wholesale, over-buffing crit damage and letting a <1 debuff push a crit below ×1.0. Now scale
   only the bonus part (`1 + (m−1)×factor`), matching the assimilation scaler.
5. **Round-limit outcome** — timeouts (both alive at the configured cap, not just at 100) are
   now flagged `winner_by_round_limit` and are always a loss (no loot/kill on timeout); the
   hull-comparison tiebreak at round 100 was removed. See DESIGN.md §4.4.
6. **Validation** — misspelled `stat_modify` stats (which compile to nothing) now emit a
   validation warning instead of passing silently.

Report-only (documented, intentional): outbound morale mitigation is skipped for defenders
without `hostile_mitigation_params` (PvP-shaped/legacy only); counter-fire player mitigation is a
sheet-style model without hostile piercing/accuracy terms (DESIGN.md §3.5);
`combat_battle_type_id` is never set, so `CombatBattleTypeAny` conditions are leniently true;
decay/accumulate curves count round 1 as one step (DESIGN.md §3.3, now documented).

## 1. Faction-gated lethal strikes (Q/faction elite hostiles — ~123 hostiles) ✅

**Status (2026-07-08):** Implemented — `HostileLethalUnlessAttackerFaction` +
`HostileAttackerShieldMitigationZero`; catalog bucket `faction_gate_lethal`; coverage in
`tests/hostile_fidelity_new_mechanics.rs`.

**a) The issue.** Five text families make a hostile *unengageable* except by specific ship
factions: Tal Shiar Elite (`2518573064`, 30 hostiles, "only Federation or Klingon designed ships"),
Mo'Kai Elite (`1651219904`, 30, Fed/Romulan), S31 Elite (`1088929105`, 30, Klingon/Romulan),
and the Q hostiles Almost Omnipotent (`1206267116`, 17) and Strike Down (`1567589326`, 16,
"Federation, Romulan, and Klingon ships, or the U.S.S. Vengeance"). Any other ship is "lethally
struck at the start of combat" — an instant loss. Today these are `combat_noop`, so the simulator
happily reports win rates for ships that cannot even enter the fight, which can mislead the
optimizer's ship recommendations. Strike Down additionally zeroes the player's Shield Mitigation
for the whole fight, and both Q variants give the hostile a 300% Critical Damage Floor — those
secondary effects map to hooks that already exist (`hostile_crit_damage_floor`; shield-mitigation
debuff needs checking).

**b) Prompt.**

```

6. Update docs/HOSTILE_ABILITY_COMBAT_NOOP_AUDIT.md (bucket table + fidelity-pass section) and

interact with ranking (win_rate 0 is the correct signal).
```

## 2. Per-hit stacking counter buffs — Critical Breach / Rising Fire (34 hostiles) ✅

**Status (2026-07-08):** Implemented — `DefenderOnHitStack` + Hole Puncher / Immolator combat-begin
player breach/burn; catalog bucket `defender_on_hit_stack`; coverage in
`tests/hostile_fidelity_new_mechanics.rs`.

**a) The issue.** Two Xindi-era abilities stack a buff *per weapon hit* with a 2-round expiry:
Critical Breach (`3358683912`, 17 hostiles) "increases its Critical Chance by X% for 2 rounds
every time it hits with a weapon **while the player is Hull Breached**" (plus a 150% crit floor),
and Rising Fire (`3353377682`, 17) "increases its standard damage by X% for 2 rounds every time it
hits **while the player is Burning**". The engine has no defender-side per-hit stack mechanism, so
both are noop. These hostiles synergize with their own breach/burn appliers — the sim currently
underestimates them badly in longer fights. The attacker side already has an analogous mechanism
(`OnHitCritDamageStack` with `on_hit_crit_stack_expires` ring in `CombatRunState`), and the
defender side already tracks expiring entries for shots (`defender_shots_bonus_entries` with
`expires_round`), so the pattern to copy exists.

**b) Prompt.**

```
  hull-breached adds +X% crit chance to the defender for 2 rounds (stacks); extra seat: hostile
```

(`hostile_crit_damage_reduction`, multiplicative fraction path) still multiplies the hostile's
*full* crit multiplier: `crit_mult × (1 − reduction)`, which can push a crit below ×1.0 — i.e.

which convention is right, which needs community evidence rather than code archaeology.

full-multiplier convention for the mitigation/percentage family. (`crit_mitigation_rating`,
